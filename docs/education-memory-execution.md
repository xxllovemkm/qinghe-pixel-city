## 4. 来源与课程实施要求

### 4.1 来源提取与迁移

每个派生目标至少保留：源文件相对路径、源文件哈希、资源 ID、原始片段、提取后目标文本、提取器版本、目标内容哈希、图谱版本。

对栏目边界先建立已知问题样例，再扩展到各学段、各学科的真实格式。完整导入生成机器可读报告，列出总数、完整数、缺失数、确认顺序数和待确认数。抽样清单在检查前冻结，覆盖所有实际来源学科和学段，以及缺失字段与顺序歧义。

旧到新节点映射保存映射类型、依据、审核状态与适用图谱版本。拆分和合并节点的掌握状态如何处理必须显式定义；不确定映射保留待审核状态。至少验收：原文不变、删除栏目污染、一分多、多合一、未知映射、重启后读取旧运行。

### 4.2 课表与课时目标

每个实际课时保存如下追踪链：

```text
年级／学期／学校排课政策版本
  → 教材版本／单元／课时来源／顺序证据
  → 原教学目标
  → 本课承担的目标与后续课时承接
  → 活动／题目／评分与观察依据
```

周课表与教材课序分别验证。来源不足或必需的实践、语音、图像能力未满足时，预览给出具体课时和原因。连续三天的课段必须按正常课程顺序可执行。

### 4.3 作业量与证据类型

每课保持12–20题的完整作业。先给整天分配90分钟预计预算，再按课程目标设计题目复杂度、短题与综合题比例、实践安排，最后加总逐题时间。预算只采用可信的任务估计，附估计依据与不确定性；课堂任务时长与家庭作业时长分别记录。

每道题定义所需证据类型和可评价维度。例如朗读题区分文本停连设计与声音表现：文字可支持前者，声音证据支持后者。提交状态、判定状态、分值、评价原因和掌握贡献分别保存。APP 与 Judge 共享明确的评分语义，Judge仍独立依据题目和原答求解。

专项数据至少覆盖：正确、错误、部分分、空答、证据缺失、提示后订正六类，每类至少两例。规则测试可使用固定输入；真实模型案例标明自然出现或人工编制，分别报告分母。

## 5. 对话和 Memory 实施要求

对话状态至少明确当前作业、题目、小问、最新对方消息、待回应消息、原已尝试步骤、尚未解决点和下一步行动。实际消息保存 `response_to_id`；恢复后接续该身份。

设定每份作业最多3个学生—APP交换周期。若最后一条 APP 消息包含新问题，任务状态应标记等待后续回应，并保留该问题；教学完成和批改完成具有独立状态。

Memory 审核必须同时检查：

- 记录实际使用了哪条学生原话、原答、评分或后续表现。
- 当前题的直接证据与跨题历史证据分别有合法归属和关联理由。
- 已有记忆是否参与了后续讲法、诊断或练习选择，并有调用时的实际输入佐证。
- 实际学生回应是否支持此次掌握更新，量规版本、证据权重与去重行为是否一致。
- APP 请求所见信息与该角色可得证据一致；人物设定和模拟器真实掌握用于学生行为生成。

同一作答重评、重复请求和服务重启均需验证幂等；新判断保留可追踪的变化原因。个人图谱节点含掌握度、星级、更新时间、来源和证据跳转，显示数值与后端投影一致。

## 7. 真实 API 实验边界

所有模拟和独立 Judge 均使用配置中的 LiteLLM。生成模型与 Judge 分别记录配置；独立评测至少具有独立提示、冻结输入和任务身份，明确是否使用同一底层模型。

| 批次 | 内容 | 请求总上限 | 实际并发上限 | 累计有效执行时间上限 |
| --- | --- | --- | --- | --- |
| 开发与专项 | 六学科已知问题、评分专项、至少六个完整对话案例 | 180 | 8 | 1,800秒 |
| 冻结课程验收 | 每学科一个新课时，共6课；生成与独立审核 | 48 | 8 | 900秒 |
| 三天联合运行 | 3学生×3天×6课、每份12题、每份最多3轮、3份外来材料 | 1,200 | 8 | 7,200秒 |
| 三天独立评测 | 75个主任务＋6个外来材料任务 | 110 | 8 | 1,800秒 |

以上是上限，不是目标请求量；重试、局部修复、手工续答、材料处理和连通性验证计入相应批次。总上限1,538次请求；已知累计 token 上限30,000,000，最终请求可能产生的尾部用量单列。开始前报告预估请求量和按本地已配置价格计算的费用；价格未知则记录未知及请求／token边界。

预算执行要求：

1. 将人数、课表、每份作业题数、轮数、种子、模型、来源、预算写入 manifest。配置上限与真实网络峰值分别记录。
2. 所有子通道共用本批次总量核对；服务恢复沿原账本计数。控制接口变更预算时写入审计记录。
3. 同一逻辑请求自动修复最多2次；仍失败则暂停该任务、保存诊断及原响应，先做离线修复。
4. 达到请求、token或时间上限后保留检查点和未完成清单，停止新增请求。扩大上述实验边界应交回用户决定。
5. 未知 token 用量单独计数，不能按零计入“精确费用”。发生未知用量先核对网关记录；请求与时间上限始终生效。
6. 每30–60秒保存紧凑进度：运行状态、课时数、逐学生作业数、提交数、评分数、对话状态、Memory数、请求完成／拒绝／失败／在途数、token及累计时间。

三天模拟固定随机种子2417，人物配置在首个请求前保存。课表可执行性预检覆盖全部18课；若来源不完整，先修复课程绑定或补全确有来源的资料，并保存新清单。运行中途修改课程、提示词或逻辑后，标注为开发运行；最终验收另用冻结版本产生完整结果。

## 8. 独立教学评测与争议裁决

每个 Judge 任务保存：输入快照哈希、提示词版本、模型、原响应、用量、评语、问题位置、严重级别和结果。评测器只读取评测所需证据；原题答案和实施模型自评分不能替代独立解答。

| 类别 | 必查内容 | 通过条件 |
| --- | --- | --- |
| 课程 | 来源、目标覆盖、实践要求、活动执行、时长、题目科学性、作业负荷 | 全部任务完成；重大问题为零；needs_review有逐项裁决 |
| 批改 | 对照原题逐题求解、原答、部分分、证据缺失、满分和反馈 | 全题覆盖；严重误判为零；每个分歧给出原题级裁决 |
| 对话 | 接续最新消息、讲解正确、学生实际回应、后续验证与结束状态 | 至少六类专项有证据；完整会话重大问题为零 |
| Memory | 本人归属、同题与跨题证据、掌握更新、后续使用 | 结构归属全部通过；语义抽查的重大问题关闭 |

重大问题定义：科学性错误、关键目标遗漏、实践被无法证明的表现替代、实际无法执行的活动、跨学生证据、未验证即判掌握、严重评分错误、来源身份失配。一般措辞或呈现问题作为轻微问题登记，说明影响。

Judge 的 `needs_review` 是待裁决状态。实施模型可以整理证据和提出判断，最终独立验收模型逐项裁决；涉及学科歧义而证据不足时保留待确认。每项记录“题目／原答／APP判定／Judge判定／采用量规／裁决与依据”。

统计按有效分母：计划课时、完成课时；布置、已答、空答、整份提交；有批改记录、可判分、待补证据；正确、部分分、错误；对话待回应、教学完成分别报告。所有交付中的“通过”都指明对应层次。

`handoff.md` 必须使验收者独立完成以下工作：

1. 启动实际前后端并打开指定运行。
2. 对照前后端修改文件、源码版本和基线。
3. 复跑工程检查与只读审计。
4. 找到每个重大缺陷的原案例、改动、回归、冻结验收结果。
